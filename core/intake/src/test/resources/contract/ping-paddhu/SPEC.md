# Ping <-> Paddhu Pusthakam contract

This folder is **identical in both repositories** (`adssaketh/Ping` and `adssaketh/Paddhu-Pusthakam`, in `contract/ping-paddhu/`). Both CIs run tests against it, so neither app can drift. Samples and golden vectors are generated by `native/tools/contract/gen-contract.mjs` in Ping (CI fails on any difference) and are all invented data.

Status marks: **[6a]** built in Ping (native), **[6b]** Paddhu side, **[6c]** logos. Anything not marked 6b/6c is already how the apps behave today.

## 1. Parties
- Paddhu Pusthakam: applicationId `com.mansaketh.paddhupusthakam`.
- Ping: applicationId `com.ping.sms` (the `prod` build). The `dev` build (`com.ping.sms.dev`) never talks to Paddhu: it shows the JSON in its Logs screen.
- Ping's manifest keeps `<queries><package android:name="com.mansaketh.paddhupusthakam" /></queries>`.
- Release order for changes: Paddhu update first, then Ping. Every change is additive: an old Paddhu works with a new Ping and a new Paddhu works with an old Ping.

## 2. The JSON (`schema/paddhu-sms-export.schema.json`)
```
{"app":"Ping","type":"paddhu-sms-export","version":1,["createdAt":<ISO>,]"from":<ms>,"to":<ms>,
 "sms":[{"id","address","body","date", [brand, brandKey, kind, category]}]}
```
- Paddhu rejects anything whose `type` is not `paddhu-sms-export` or that has no `sms` list. Keep `version: 1`.
- **Unknown fields are ignored** by readers. That is what makes the optional fields safe.
- Optional fields per item **[6a, written by Ping]**: `brand` (display name), `brandKey` (logo key), `kind` (`transaction` | `fixed_deposit`), `category` (`personal` | `transactions` | `services` | `promotions`). Never personal data: only what Ping knows about the SENDER. `brand` and `brandKey` are written once the logo system exists **[6c]**.
- `kind`: a message that matches the fixed-deposit pattern is `fixed_deposit`, even if it also matches the transaction pattern (decision of 6a). Paddhu may use `kind` to route and MUST fall back to its own detection when `kind` is absent or unknown **[6b, done in Paddhu: `fixedDepositOfPingItem` in `pingImport.dart`; `kind: transaction` is not tried as a deposit]**.

## 3. Never change (Paddhu de-duplicates on these)
- The id rules (section 4), the `body` text (including multipart join order), the timestamp column (`Telephony.Sms.DATE`, not `DATE_SENT`), and the raw `address` (`AX-AXISBK-S` is sent as is).
- Paddhu de-duplicates by id **or** by content key: day of `date` in the **phone's local time zone** + `-` + FNV-1a-32 (lower-case hex, no padding, over UTF-16 code units) of the body with whitespace runs replaced by one space and trimmed (`pingImport.dart`, `_contentKey`). Vectors: `golden/ids-and-keys.json` (computed for `Asia/Kolkata`; Paddhu tests must run with `TZ=Asia/Kolkata`). Known limit, not changed: if the phone's time zone changes between two sends, the day part can differ.

## 4. SMS ids
- Notification button and automatic send: `"n" + timestampMs + "-" + Integer.toHexString(body.hashCode())` (Java `String.hashCode`, UTF-16 code units, two's complement printed as unsigned hex).
- Date range: the phone's SMS `_id` as a string.
- Long-press: the phone's SMS `_id`, or `ping-<id>` for a message that only exists in Ping.

## 5. The three hand-over paths
1. **Single message** (notification button "Add to Paddhu", long-press on a message): explicit `ACTION_SEND` to `com.mansaketh.paddhupusthakam.ShareReceiverActivity`, type `text/plain`, JSON in `EXTRA_TEXT`, `FLAG_ACTIVITY_NEW_TASK`. Not installed: "Paddhu Pusthakam is not installed on this phone". Samples: `samples/long-press.json` (with `createdAt`, no enrichment, as today).
2. **Automatic send** (Settings > Send new bank messages automatically) **[6a delivery rebuilt]**: `ContentResolver.call(content://com.mansaketh.paddhupusthakam.pinginbox, "enqueue", json, null)` from a background thread; success only when the reply has `ok=true`. Sent only when the switch is on, the sender is not a phone number, and the text passes the transaction or fixed-deposit test; spam and blocked senders are never sent. Provider limits: 20,000 characters per JSON, 2,000 waiting files. Samples: `auto-send-single.json`, `auto-send-fixed-deposit.json`, `legacy-minimal.json` (what an old Ping sends).
3. **Date range** (Settings > Send to Paddhu Pusthakam): file `ping-sms-for-paddhu.json` in Ping's cache folder, shared as `application/json` with `EXTRA_STREAM` through the FileProvider `<applicationId>.fileprovider` (read permission granted), chooser title "Send to Paddhu Pusthakam". Only received messages of business senders (conversation not `personal`, address not a phone number) that pass the transaction test, oldest first, id = system `_id`. Sample: `samples/date-range.json`. **Fixed deposits are NOT included in this file until the updated Paddhu is installed**: the updated Paddhu imports them from this file **[6b, done]**, so Ping flips `PaddhuRange.INCLUDE_FIXED_DEPOSITS` in the release sequence of Phase 7, after Paddhu. An old Paddhu that receives such a file skips the deposit message (no error).

## 6. Delivery guarantees of automatic send **[6a]**
- Every message is stored in Ping's Room outbox (`paddhu_outbox`) before the first attempt, de-duplicated by id, and removed from the waiting list only when Paddhu answered `ok=true`. Nothing is dropped silently.
- Delivery is one unique WorkManager chain with exponential backoff (30 s start), run on: a new bank SMS, the app opening, the switch being turned on, a phone boot, and every 6 hours while the switch is on.
- If Paddhu cannot be reached (not installed, `caller not allowed`, inbox full, no answer) the run stops and everything stays queued; a refusal `nothing usable was sent` concerns that message only and the run continues.
- The status line in Ping's Settings (installed, last sent, waiting, last error) reads from the outbox.

## 7. Security
- `PingInboxProvider` accepts only the calling package `com.ping.sms` **[today]** and additionally Ping's signing certificate, pinned by SHA-256 digest **[6b]**: `12cb1f4ff2ddcd91feda62d09f555ccc6c10a8f270c031908e6ee38dec20a502`. The `prod` APK must be shown to have the same digest (CI check, 6b).
- Ping's logo provider **[6c]**: `<applicationId>.logos`, read-only, answers only Paddhu (package and pinned certificate).

## 8. "View SMS in Ping" **[6a Ping side, 6b Paddhu side]**
Paddhu starts Ping with an explicit intent to `com.ping.sms`: action `com.ping.sms.action.OPEN_SMS`, extras `address` (raw sender, string), `date` (long, ms), `smsId` (the phone's SMS `_id`, string). Ping needs `smsId`, or `address` together with `date`; it validates the extras, opens the chat, scrolls to the message and highlights it, and shows "Message not found" when it no longer exists. The intent only moves Ping's own screen.

**Paddhu side [6b, done]** (`pingSmsRefOfNote` in `pingImport.dart`, `pingOpen.dart`, `MainActivity.kt`): a transaction made from a Ping SMS keeps `Ping SMS #<id>` in its note, and new notes also get `Ping SMS from <sender>` (only for business-style headers, never a phone number). The button "View SMS in Ping" sends `smsId` for a phone `_id` (all digits) or `ping-<id>`; for an `n<timestamp>-<hash>` id (notification button, automatic send) it sends `date` (the timestamp inside the id) with the stored `address`. A transaction whose note says too little (an `n` id saved before the sender marker existed, a PhonePe entry) shows no button. Paddhu declares `<queries><package android:name="com.ping.sms"/>`.

## 10. Business logos **[6c]**
**Ping side** (`LogoProvider.kt`, `LogoRepository.kt`). A read-only `ContentProvider`, authority `<applicationId>.logos` (`prod`: `com.ping.sms.logos`; the test build `com.ping.sms.dev` has none and Paddhu never asks it). It is exported, so every call checks the caller: the package must be `com.mansaketh.paddhupusthakam` **and** every signing certificate of it must be on Ping's pinned list (SHA-256 of Paddhu's certificate). The pinned digest of Paddhu's certificate (read from Paddhu 5.4.15, one signer) is `946411ac038d0610e8348489d0c61834910d558a50acc4bfe083d27cfc4b0f03` (`LogoAccess.PADDHU_CERT_SHA256`); an empty list would refuse everybody. Only `openFile` in mode `r` works; everything else returns nothing.
- `content://com.ping.sms.logos/brand/<brandKey>` or `content://com.ping.sms.logos/sender/<raw sender, URL-encoded>`. A sender is resolved through Ping's own brand table, so Paddhu needs no table (phone numbers have no brand and are refused as "no such brand").
- Answer: the image bytes (WebP or PNG, at most 600 KB) or `FileNotFoundException` when there is no logo. A logo Ping does not have yet is fetched on the spot (Logo.dev, then Google's favicon service; only the brand's website name is sent). Paddhu never fetches logos from the internet.

**Paddhu side** (`pingLogo.dart`, `MainActivity.kt` method `getLogo` on the channel `com.mansaketh.paddhupusthakam/ping`). Before reading, Paddhu checks that the provider of that authority belongs to `com.ping.sms` and that Ping carries the pinned certificate of section 7. Logos are kept in Paddhu's cache for **24 hours** (the online logos Ping gets may not be stored longer). Shown on: the review list of messages Ping sent, and on a transaction made from a Ping SMS (next to "View SMS in Ping"). When there is no logo, no Ping, an older Ping, or Ping does not know this Paddhu yet, the screens look as they did before. The key is the optional `brandKey` of an item (`^[a-z0-9]{1,40}$`; anything else is ignored); without it Paddhu asks by the sender header stored in the note (`Ping SMS from <sender>`).
